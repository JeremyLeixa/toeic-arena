# Audit technique — Auth + Data Sync — 2026-04-21

**Scope** : flows d'authentification, identité utilisateur, sauvegarde/chargement Supabase, onboarding, magic link. Read-only, zéro modification de code.

**Verdict global** : le système a accumulé des couches successives (PIN → magic link → soft logout → stale guard → phantom guard → session recovery) sans qu'une couche supporte clairement les hypothèses d'identité de la suivante. **Trois incohérences fondamentales** se combinent pour produire la majorité des symptômes observés.

---

## 🧭 Section 1 — Les 3 incohérences fondamentales

### Incohérence #1 : l'identité est à la fois `(name, class_code)` ET `students.id`

Selon le code qu'on lit, **on ne sait jamais laquelle fait foi** :

| Opération | Clé utilisée |
|-----------|-------------|
| `save()` UPDATE | `(name, class_code)` |
| `save()` INSERT | `{id: auth.user.id, name, class_code}` |
| `load()` primary | `(name, class_code)` depuis localStorage |
| `load()` fallback | `students.id = auth.user.id` |
| `recover()` | `(name, class_code)` puis **UPDATE id pour rebinder** |
| Phantom guard | `name` seule |

Résultat : un même étudiant peut exister avec plusieurs combinaisons (name, class, id) possibles. Quand le localStorage est vide et que `auth.user.id` a changé (anon session renouvelée), le fallback-by-id renvoie potentiellement une AUTRE row que celle attendue — ou aucune.

### Incohérence #2 : les sessions anonymes Supabase sont ÉPHÉMÈRES, mais on les utilise comme identité permanente

`supabase.auth.signInAnonymously()` est appelé à **6 endroits** :
- [App.jsx:514](src/App.jsx:514) dans `ensureAuthSession` (fallback)
- [App.jsx:1149](src/App.jsx:1149) dans `lookupName`
- [App.jsx:11405](src/App.jsx:11405) dans `onboard`
- [App.jsx:11441](src/App.jsx:11441) dans `recover`

**Chaque appel crée un NOUVEAU `auth.users` row avec un NOUVEAU `user.id`**. Les anon users :
- Peuvent expirer / être nettoyés par Supabase (JWT expire ~1h, refresh token plus long mais pas infini)
- Ne peuvent pas être "retrouvés" — il n'y a pas de "signInWithExistingAnon(id)"
- Accumulent dans `auth.users` (pollution)

Conséquences concrètes :
- **Teacher** a sa row `students` liée à un anon user créé la 1ère fois. Si cette session expire / l'user est nettoyé, `students.id` pointe vers un fantôme
- À chaque "Changer de profil" suivi d'un retour : si la session expire entre-temps, une nouvelle anon session est créée → `user.id` différent → fallback-by-id échoue
- Le "rebind id" dans `recover()` ([App.jsx:11449](src/App.jsx:11449)) **n'a aucun effet durable** si la session est à nouveau perdue plus tard

### Incohérence #3 : le bouton "Changer de profil" et l'onboarding reposent tous les deux sur `lookupName`, mais `lookupName` peut être bloqué par RLS

`lookupName` fait `SELECT name, class_code, xp FROM students WHERE name ILIKE ...`. Si RLS restreint la SELECT pour les sessions anonymes fraîches (ce que ton comportement Teacher suggère), cette query renvoie 0 rows **même si la row existe**. L'étudiant est alors forcé dans le flow "new user" → `fresh()` → `tutorial_pending=true`.

**Je ne peux pas voir tes policies RLS**, mais le symptôme que tu as décrit ("je tape Teacher, on ne me propose pas Welcome back, je vois Join a Group") est typique d'un RLS qui filtre les SELECT par appartenance.

## 🐛 Section 2 — Bugs catalogués

### 🔴 CRITIQUE

#### B1. `recover()` — UPDATE de `students.id` peut échouer silencieusement
[App.jsx:11448-11451](src/App.jsx:11448)
```js
if(d.id!==userId){
  await supabase.from('students').update({id:userId}).eq('id',d.id);
  _cachedUserId=userId;
}
```
Le résultat de l'UPDATE n'est pas vérifié. Si RLS bloque (très courant sur la colonne `id`), la modification n'a pas lieu. Le prochain load par auth.id ne trouve toujours rien. L'étudiant doit re-passer par lookupName à chaque ouverture.

**Aggravant** : modifier la colonne `id` (primary key probable) est une opération risquée. Supabase peut explicitement l'interdire via policies.

#### B2. `ensureAuthSession()` crée silencieusement un **nouveau** user_id anonyme
[App.jsx:513-516](src/App.jsx:513)
```js
var anon=await supabase.auth.signInAnonymously();
```
Appelé depuis `save()`. Chaque fois que la session expire, un nouvel anon user apparaît. Conséquences en cascade :
- L'email linké via magic link est sur l'ANCIEN anon user. Le nouveau user n'a pas d'email.
- Les Stripe customers côté serveur sont liés à l'ancien user_id.
- Le fallback-by-id dans `load()` échoue car `students.id` pointe vers l'ancien user.

#### B3. Fallback-by-id dans `load()` peut renvoyer la **mauvaise** row
[App.jsx:450-453](src/App.jsx:450)
```js
if(!remote){
  var res2=await supabase.from("students").select("*").eq("id",userId).maybeSingle();
```
Si l'utilisateur a un row phantom (ex : row visitor avec id=current_auth.uid), ce fallback retourne le phantom en priorité. L'étudiant charge comme "visitor" même si sa vraie row existe en idrac2026.

#### B4. `saveLocal()` set `_syncDirty=true` en permanence
[App.jsx:398](src/App.jsx:398)
`_syncDirty` devient donc quasi-toujours true, sauf fraction de seconde post-load. Le flag ne joue pas son rôle de "est-ce que j'ai besoin de sync". Effet : les syncs 60s tournent pour rien, et le onUnload envoie des payloads non nécessaires.

#### B5. `signOutCompletely()` a un bug de nom de clé
[auth.js:82](src/auth.js:82)
```js
localStorage.removeItem('toeic-arena-local');  // ← clé INEXISTANTE
```
Devrait être `'toeic-arena-profile'`. Code mort actuellement (jamais appelé) mais piégeux si utilisé.

### 🟠 MAJEUR

#### B6. La boucle `[LOAD]` observée chez toi vient d'un flag mal scopé
[App.jsx:10921-10960](src/App.jsx:10921)
La variable `loaded` est scopée au useEffect mais setTimeout/onAuthStateChange peuvent fire plusieurs INITIAL_SESSION/SIGNED_IN/USER_UPDATED très rapidement. J'ai fixé ça au commit 218a9a1 mais je n'ai pas testé que ça ne CASSE pas le cas "session vraiment renouvelée plus tard" (ex : si la session se renouvelle pendant que l'user est sur l'app). Un TOKEN_REFRESHED est skippé, mais je suis pas sûr que USER_UPDATED (email confirmé) passe bien.

#### B7. Phantom guard trop agressif
[App.jsx:564-568](src/App.jsx:564)
```js
var dup=await supabase.from("students").select("class_code").ilike("name",d.name).neq("class_code",cc);
if(dup.data&&dup.data.length>0){
  console.error("[SAVE] BLOCKED: would create phantom...");
  return;
}
```
Faux positif : **deux étudiants différents** portant le même prénom dans deux classes différentes (Alice dans idrac2026 + Alice dans cesi2026). Le 2e qui arrive voit son INSERT bloqué → perd ses données.

#### B8. `onboard()` ne vérifie pas le succès du `syncToCloud` initial
[App.jsx:11421-11423](src/App.jsx:11421)
```js
_syncDirty=true;
syncToCloud(u);  // fire-and-forget, pas d'await
```
Si le premier INSERT échoue (RLS, schema, etc.), l'étudiant ne le sait pas. Sa row existe en local mais pas en DB. Symptôme "Nourene doit se retaper l'onboarding" : possible cause racine.

#### B9. `save()` INSERT utilise `{id: user.id}` — conflict possible
[App.jsx:570](src/App.jsx:570)
```js
var ins=await supabase.from("students").insert({id:user.id,name:d.name,class_code:cc,...payload});
```
Si `user.id` existe déjà dans la table (autre row de l'user), et `id` est PK unique, conflict. Erreur silencieuse (logged mais pas remontée).

#### B10. La stale-remote guard peut rejouer des saves en boucle
[App.jsx:467-482](src/App.jsx:467)
Si `local.xp > remote.xp`, elle retourne local ET appelle `save(local)`. Mais si save échoue (schema, RLS), remote reste obsolète, local.xp > remote.xp reste vrai, prochaine load → même branche → save → échec → infini.

#### B11. Multi-devices : pas de last-write-wins avec timestamps
Si l'étudiant utilise device A puis device B, le dernier save "gagne". Sans horodatage fin, un device peut overwriter des données plus récentes de l'autre si ses saves arrivent en dernier. Pas de merge intelligent.

### 🟡 MINEUR

#### B12. Build ID hardcodé [App.jsx:369](src/App.jsx:369)
`var BUILD_ID="2026-04-08a"` — incorrect depuis le 8 avril. Pas critique, juste trompeur dans les logs.

#### B13. Comportement de `fresh()` + `tutorialPending=true` systématique
[App.jsx:470](src/App.jsx:470) Chaque appel à fresh() force tutorialPending=true. Si un étudiant existant passe par `fresh()` (cas d'échec de recover), il revoit le tour guidé.

#### B14. `lookupName` normalizeName fait match exact
[App.jsx:1164](src/App.jsx:1164)
`normalizeName(s.name)===norm` — exact. Typo dans le nom ("Noureen" vs "Nourene") → pas de match. Pas de Levenshtein ou fuzzy matching.

## 🗺️ Section 5 — Cartographie des flows actuels

### Boot sequence (ouverture de l'app)
```
1. App.jsx load → module-level code (loadLocal, etc.)
2. useEffect [] → onAuthStateChange subscribed
3. Supabase hydrate from localStorage → fires INITIAL_SESSION
4. If session valid: load(userId)
   a. Fetch local profile
   b. Primary: SELECT * WHERE name ILIKE cn AND class_code = cc (if cn known)
   c. Fallback: SELECT * WHERE id = userId
   d. Stale-guard: if localXp > remoteXp, prefer local + save()
   e. Return row (or null)
5. If d exists: apply week transition, sU(d), sL(false)
6. If d null: Onboard renders
```

### Onboarding flow (si u=null)
```
Onboard "name" → user types → lookupName(n)
  ↓
  lookupName: ensure anon session, SELECT by ilike(name)
    ↓ 0 rows → "classcode" step
    ↓ ≥1 row → "recognize" step with group cards
  ↓
  recognize click → recover(name, class_code)
    ↓ finds row → UPDATE students.id = currentUserId (RLS risk)
    ↓ supaToLocal → sU → Home
  ↓
  OR classcode → consent → Battle Scan → pushPrompt → emailPrompt → langBridge → p.go
    ↓
    p.go = onboard(name, class, bs, bsCorrect, firstNav)
      ↓
      existingMatch by normalizeName + class_code
        ↓ found → recover()
        ↓ not found → fresh() + syncToCloud
```

### Save pathways
```
User action → sv(c)
  ↓
  sU(c) + saveLocal(c) [→ _syncDirty=true] + save(c) [fire-and-forget]

Plus :
- Interval 60s → applyWeekTransition + saveLocal + syncToCloud if dirty
- visibilitychange hidden → applyWeekTransition + saveLocal + syncToCloud
- visibilitychange visible → load(userId) → overwrite memory state
- beforeunload → fetch keepalive PATCH avec payload réduit
```

### Magic link (3 entry points)
```
1. Onboarding emailPrompt: linkEmailToAnonymous(email) + pollEmailConfirmation
2. Home banner "Secure your account": linkEmailToAnonymous + sessionStorage flag + polling in main App
3. Profile → Gestion compte → Sécuriser: même flow

onAuthStateChange USER_UPDATED → syncEmailFromSession → UPDATE students.email
```

## 🎯 Section 6 — Recommandations prioritaires

### Quick wins (1h, peu de risque)
1. **Fix B5** : `signOutCompletely` clé localStorage. Trivial.
2. **Fix B4** : `saveLocal` ne set plus `_syncDirty=true` automatiquement — laisser les appelants le faire.
3. **Fix B12** : update BUILD_ID ou le retirer (il ne sert à rien sauf logs).
4. **Log améliorés** : ajouter console.error dans `recover()` si UPDATE id échoue, dans `syncToCloud` si save échoue.

### Structural fixes (demi-journée)
5. **Fix B1 & B2 ensemble** : au lieu de rebinder `students.id`, stocker l'association `auth.uid → students.(name, class_code)` dans une table `user_bindings` séparée. RLS simple : `user_id = auth.uid()`. Load par binding, puis fetch par (name, class_code). Supprime tout le rebinding risqué.
6. **Fix B7** : phantom guard plus précis. Ne bloquer que si la row "même name, autre class" appartient au **même auth.uid** (via user_bindings ci-dessus). Sinon c'est un autre étudiant homonyme, pas un phantom.
7. **Fix B6 + B10** : gérer retry intelligent. Si load retourne null, attendre un vrai SIGNED_IN (pas INITIAL_SESSION). Si save échoue, ne pas retenter en boucle — back-off exponentiel.
8. **Fix B8** : `onboard()` devrait `await syncToCloud(u)` et **afficher une erreur** si l'INSERT échoue, au lieu de laisser l'user croire qu'il est onboardé.

### Refonte fondamentale (1-2 jours, critique)
9. **Repenser l'identité** : abandonner anon sessions comme clé d'identité. Soit :
   - **Option A** : forcer l'email dès l'onboarding (magic link = signin). Plus de anon du tout.
   - **Option B** : garder anon pour les visiteurs, mais associer chaque anon user à un device via localStorage (UUID généré localement), et rebinder si session perdue.
10. **RLS policies** : les auditer et documenter. S'assurer que `UPDATE students SET id` est géré proprement (ou désactivé, et on utilise user_bindings).
11. **Tests end-to-end** : même manuels, un checklist documenté "Après logout, retyper nom doit Welcome back, clicker groupe doit restaurer tout, changer device doit syncer" pour chaque commit futur.

### Safety measures (à mettre en place maintenant)
12. **Monitoring** : ajouter un global `window.onerror` qui push les erreurs JS + logs `[SAVE] BLOCKED` dans une table Supabase `error_log`. Tu sauras en temps réel quels étudiants hit quels bugs.
13. **Banner maintenance dans l'app** : afficher discrètement "Version maintenance — signalez tout souci" tant que le mode maintenance dure.
